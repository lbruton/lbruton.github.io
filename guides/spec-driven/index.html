Spec-Driven Development

Three tiers — /gsd, /sketch, /spec — powered by the SpecFlow MCP server. Pick the tier that matches the size of the work. Every tier shares the same non-negotiables: file an issue first, use a worktree, signed commits, and a PR. No code without a plan.

Overview
Three Tiers, One Philosophy

Not every change needs a dashboard. Not every fix needs a markdown artifact. The three-tier model lets the overhead match the work — a CSS tweak and a multi-component feature should not go through the same process. What never changes: an issue is filed, a worktree is used, and the code is reviewed before it ships.

/gsd

Quick fixes under ~30 min. No spec, no approval gates. Casual worktree, PR as a chore.

/sketch

Middle tier. Markdown-first phased artifacts. File-based review, no dashboard. Supports cross-model peer review.

/spec

Full workflow. Dashboard approval gates, implementation logging, multi-agent dispatch.

SpecFlow MCP server

All three tiers are powered by SpecFlow — an MCP server that ships 7 tools, 7 lifecycle prompts, and a real-time approval dashboard. It integrates directly into Claude Code as a standard MCP server. Install via npm install -g @lbruton/specflow, then add it to your MCP config.

Universal rules across all three tiers
File an issue first (tracked in Plane). Use a git worktree — never work directly on main. Signed commits + PR. No code merges without review.

Tier 1
/gsd — Get Stuff Done

/gsd is the fast path for work that's too small to justify a spec but still follows the worktree → PR discipline. The commit message uses a chore: prefix and the PR description is kept brief. No issue is strictly required, but one should be logged when the fix spans multiple files or affects runtime behavior.

When to use it

A CSS tweak, a config update, fixing a broken link, bumping a dependency, renaming a variable. If the work takes longer than ~30 minutes or touches more than a handful of files, promote to /sketch.

$ /gsd 1. Worktree ──▶ create isolated branch 2. Fix ──▶ edit 1–3 files 3. Commit ──▶ chore: <message> (signed) 4. PR ──▶ open, squash-merge, delete branch
Scope creep check
If you're mid-fix and realise the change is bigger than expected — stop. Commit what you have, open a /sketch or /spec for the rest, and link the issues.
Tier 2
/sketch — Phased Markdown Artifacts

/sketch is the middle tier: structured enough to catch design mistakes, lightweight enough to avoid dashboard overhead. Every phase produces a markdown file. Review happens file-by-file, not through a dashboard. A /sketch can be promoted to /spec at any point if the scope expands.

The four sketch phases

Requirements

User stories, acceptance criteria, non-functional requirements.

Discovery

Codebase search — what already exists, what patterns to reuse, potential ripple effects.

Approach

2–3 implementation options, trade-offs, and the chosen direction.

Tasks

Atomic steps. Each task is reviewed, implemented, and marked done directly (no log-implementation call).

Cross-model peer review with /sketch-review

/sketch supports a dedicated review step at any phase boundary. A reviewer agent — often a different model running in a separate terminal — runs /sketch-review, which checks the phase artifact against the live codebase and flags conflicts, missing edge cases, or design gaps. This is agent-agnostic: the reviewer can be Claude Opus, a Gemini instance, or any other model that has MCP access.

$ /sketch ISSUE-ID requirements.md ──▶ review ──▶ discovery.md ──▶ review │ ▼ approach.md ──▶ review ──▶ tasks.md │ implement, mark [x] │ PR + merge
Promote to /spec when…
…the approach phase reveals cross-cutting concerns, the task count exceeds ~8, or you want parallel agent dispatch. Just run /spec ISSUE-ID --from-sketch and the existing artifacts carry over.
Tier 3
/spec — Full Dashboard-Gated Workflow

/spec is the full workflow for non-trivial features. Every phase is approval-gated through the SpecFlow dashboard before the next phase begins. Implementation tasks are logged — creating a searchable record of every file, endpoint, and component added — so future specs never duplicate work.

The four spec phases

1. Requirements

WHAT are we building? User stories, acceptance criteria, non-functional requirements.

2. Design

HOW will it work? Architecture, components, data models, error handling. Always references the codebase search.

3. Tasks

Atomic steps with _Prompt, _Leverage, and file touch maps for parallel dispatch.

4. Implementation

Subagent dispatch, spec compliance review, code quality review, log-implementation, then ship.

Phase 1: Requirements ── APPROVAL ──▶ Phase 2: Design │ │ codebase-search APPROVAL Impact Report │ ▼ Phase 3: Tasks ── APPROVAL ──▶ Phase 4: Implementation │ For each task: ├── Implement ├── Review (spec + quality) ├── log-implementation └── Mark [x]

Codebase search is a hard gate

Before requirements are written, Claude runs a codebase search to understand what already exists. This produces an Impact Report showing files likely to be touched, existing patterns to reuse, and potential ripple effects. The search uses structural (graph DB) and semantic (vector DB) tools to find related code. No requirements get written without it.

Requirements document structure

.spec-workflow/specs/PROJ-498-price-scraper-fix/requirements.md

## References
- Issue: [[PROJ-498]]
- Spec path: .spec-workflow/specs/PROJ-498-price-scraper-fix/

## Requirements

### Requirement 1: eCheck Price Accuracy
**User Story:** As a user viewing JM Bullion prices, I want to see
the eCheck/Wire price, so that I can compare actual purchase costs.

**Acceptance Criteria:**
1. WHEN displaying JM Bullion prices THEN the eCheck/Wire column
   SHALL be read, not Card/PayPal
2. WHEN other vendors are displayed THEN their prices SHALL be
   unaffected by this change

## Non-Functional Requirements
- Performance: Price extraction under 200ms per vendor
- Reliability: Graceful fallback if column structure changes
Acceptance criteria must be testable
Write criteria as "WHEN X THEN Y SHALL happen" — behavioral statements that can be verified in tests. Avoid vague criteria like "prices should be correct."

The _Prompt pattern (Tasks phase)

Every task includes a _Prompt field with four components: Role, Task, Restrictions, and Success criteria. This is the instruction block that a subagent receives when implementing the task. The file touch map is used by the orchestrator to batch non-overlapping tasks for parallel dispatch.

tasks.md (example task)
## Task 1.1: Fix Price Column Selection
- [ ] Update column-aware parser to check eCheck first
- [ ] Add regression test for JM Bullion parsing

_Prompt: Role: Backend Developer specializing in web scraping |
  Task: Fix price-extract.js to read eCheck/Wire column before
  Card/PayPal column in JM Bullion parser |
  Restrictions: Don't change other vendor parsers. Don't modify
  the DOM query selectors — only change the column selection
  order. |
  Success: eCheck prices within $5 of website values for all
  JM Bullion products.

_Leverage: devops/pollers/shared/price-extract.js (existing parser)
_Leverage: devops/pollers/shared/vendor-config.js (column mappings)

_Requirements: Requirement #1, Acceptance Criteria #1, #2

Implementation logging

The log-implementation tool creates a searchable record of what was built: files modified, API endpoints created, components added, test results. Future specs check these logs to avoid creating duplicate endpoints or reimplementing existing components. This is what makes the system self-aware across specs.

log-implementation
  specName: "PROJ-498-price-scraper-fix"
  taskId: "1.1"
  summary: "Fixed column selection order in JM Bullion parser"
  filesModified: ["devops/pollers/shared/price-extract.js"]
  artifacts:
    functions:
      - name: jmPriceFromProseTable
        location: "price-extract.js:142"
    tests:
      - name: "JM Bullion eCheck prices"
        status: "passed"
        count: "4 passed, 0 failed"
Hard gate — /spec only
Never mark a task [x] in a /spec without calling log-implementation first. (/sketch marks [x] directly — no log-implementation call.)

Multi-agent dispatch

Tasks with non-overlapping file touch maps can be batched and dispatched to parallel subagents. The orchestrator reads each task's file list, identifies safe-to-parallel groups, and launches agents concurrently. Implementation logs from completed tasks prevent a second agent from duplicating work already done by a first.

# Tasks with no file overlap → dispatch in parallel
Task 1: MODIFY price-extract.js, TEST price-extract.test.js
Task 2: MODIFY retail-display.js, TEST retail-display.test.js
         ↑ No overlap → parallel safe

# Tasks sharing files → run sequentially
Task 3: MODIFY price-extract.js ← conflicts with Task 1
         ↑ Overlap → must wait for Task 1

Bootstrapping SpecFlow

SpecFlow ships as an npm package. Install it, add the MCP server to your Claude Code config, and the /gsd, /sketch, and /spec skills become available immediately.
