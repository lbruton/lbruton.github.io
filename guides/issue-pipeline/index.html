Issue & Task Pipeline

Every code change starts with a Plane issue. Full lifecycle from creation to close — driven by Claude Code skills and MCP tools, with SpecFlow gates for non-trivial features.

Why This Exists
Issue Tracking That Claude Can Drive

The core requirement is simple: Claude Code needs to be able to create, read, and update issues without leaving the terminal or breaking the flow of a session. The mechanism has evolved over time.

Earlier, issues lived as markdown files with YAML frontmatter in an Obsidian vault, with Obsidian Bases providing database-style views. That worked — Claude could read and write the files directly — but it introduced friction: counter files to increment, frontmatter quoting rules to enforce, and a separate vault to keep in sync with the codebase.

The setup now runs on Plane — a self-hosted issue tracker with a full REST API — accessed through the mcp__plane__* MCP tool suite. The /issue skill dispatches to whichever backend the project declares in .specflow/config.json. The issue lifecycle narrative is the same; the mechanism is more reliable.

Capability Old (markdown + Obsidian Bases) Current (Plane + MCP)
Issue creation Write a markdown file, bump a counter mcp__plane__create_issue — one call
Status updates Edit frontmatter field mcp__plane__update_issue by readable ID
Issue listing Obsidian Bases query or grep mcp__plane__list_project_issues
Cross-project view Vault-root Issues.base file Plane workspace dashboard
Comments Body of the markdown file mcp__plane__add_issue_comment
Project config .claude/project.json with vault path .specflow/config.json with issue_backend: "plane"

Configuration
Per-Project Config

Each project declares its issue backend and Plane coordinates in .specflow/config.json. The /issue skill reads this file to know where to route.

.specflow/config.json 
{
  "project": "Portfolio",
  "issue_prefix": "WWW",
  "issue_backend": "plane",
  "plane_workspace": "lbruton",
  "plane_project_id": "8267e307-d3b9-48f2-8bbe-1f4cc961e63a"
}

Project Prefixes

Each project gets a short prefix that becomes the human-readable part of every issue ID. Plane generates the numeric suffix automatically.

PrefixProject
WWWPortfolio (lbruton.cc)
STRKStakTrakr
OPSDevOps / Infrastructure
SWFSpecFlow Plugin
UUID stability
Plane issue and state IDs are UUIDs that go stale across sessions and after compaction. Always fetch issues by readable identifier (e.g. WWW-12) using get_issue_using_readable_identifier, and fetch states by display name using list_states. Never copy raw UUIDs from memory or session summaries — re-fetch them.
Skills
Issue Lifecycle Skills

A small set of Claude Code skills covers the full issue lifecycle. Each skill is a SKILL.md file that Claude reads and follows — they route through MCP rather than writing files directly.

/issue

Create or update an issue. Reads .specflow/config.json, dispatches to the declared backend, and returns the readable ID (e.g. WWW-12).

/spec

SpecFlow-driven development. Takes an issue through Requirements, Design, Tasks, and Implementation with approval gates at each phase.

/sketch

Mid-weight alternative to /spec. Phased markdown artifacts without dashboard gates — useful for features that need design thinking but not full SpecFlow ceremony.

/gsd

Get Stuff Done — lightweight path for trivial fixes. Opens a worktree, ships a chore PR. No issue, no spec unless the fix grows.

/plane-archive

Archive Done and Cancelled issues in Plane. Keeps the active board clean without permanently deleting history.

/issue Skill Workflow

1. Read .specflow/config.json → get issue_backend, prefix, plane_project_id
2. If issue_backend == "plane":
   a. Call mcp__plane__list_states to resolve state UUID by display name
   b. Call mcp__plane__create_issue with title, description, state, priority
   c. Return readable identifier (e.g. WWW-12)
3. Confirm: "Created WWW-12: [title]"

Querying Issues in a Session

Use mcp__plane__list_project_issues scoped to the current project for a focused view. For cross-project views, use the Plane workspace dashboard. Never glob across all projects unless the user explicitly requests a cross-project summary.

# Check open issues for the current project
mcp__plane__list_project_issues
  workspace_slug: "lbruton"
  project_id: "8267e307-..."   # from .specflow/config.json

# Fetch a specific issue by readable ID
mcp__plane__get_issue_using_readable_identifier
  workspace_slug: "lbruton"
  project_identifier: "WWW"
  sequence_id: 12
Spec Workflow
Issue → Spec → Ship

Non-trivial features go through a four-phase SpecFlow workflow. Each phase produces a document, requires a dashboard approval, and feeds into the next phase. The Plane issue tracks overall state; SpecFlow tracks implementation detail.

The Four Phases

PhaseDocumentQuestion
1. Requirementsrequirements.mdWHAT are we building and for whom?
2. Designdesign.mdHOW will it work technically?
3. Taskstasks.mdWhat are the atomic steps?
4. ImplementationCode + logsBuild it, review it, ship it.
# Spec files live in the project's .spec-workflow directory
.spec-workflow/specs/WWW-12-add-dark-mode/
  ├── requirements.md      # User stories, acceptance criteria
  ├── design.md            # Architecture decisions, component design
  ├── tasks.md             # Atomic tasks with _Prompt guidance
  └── Implementation Logs/
      ├── Task-1-log.md    # What was built, files changed
      └── Task-2-log.md

Implementation Logging

Before marking any task [x] complete in a /spec workflow, the log-implementation tool must be called. This creates a searchable knowledge base of what was built. The /sketch workflow marks tasks complete directly without a log-implementation call.

When to skip the spec
Simple bug fixes and chores don't need a full spec. Use the bug fast path: /systematic-debugging → /issue → fix → PR. Or for trivial fixes, use /gsd — no issue, no spec, just a chore: PR.
MCP Reference
Plane MCP Tool Suite

The mcp__plane__* tools provide direct API access to the Plane issue tracker. These are the primitives the /issue skill and Claude Code sessions use — no browser, no manual UI needed.

ToolWhat it does
create_issueCreate a new issue with title, description, state, priority, and labels
update_issueUpdate any issue field — state, priority, assignee, title
list_project_issuesList all issues for a project, optionally filtered by state or priority
get_issue_using_readable_identifierFetch a single issue by its human-readable ID (e.g. WWW-12) — the stable lookup key
add_issue_commentAdd a comment to an issue — used during implementation to log progress
list_statesFetch all states for a project — required to resolve state UUIDs before create/update
get_projectsList all projects in a workspace — useful for cross-project lookup
Self-hosted, so no SaaS dependency
Plane runs on a home server behind a Cloudflare tunnel. The MCP server points at the local instance. No data leaves the network; no per-seat subscription required. The trade-off versus fully managed SaaS is that uptime depends on the home server — which is acceptable for a solo development workflow.
Quick Start
Add Plane Issue Tracking to a Project

1. Create the project in Plane

Create the project in the Plane UI or via mcp__plane__create_project. Note the project UUID — you'll need it for the config file.

2. Add the config file

# .specflow/config.json
{
  "project": "MyProject",
  "issue_prefix": "PROJ",
  "issue_backend": "plane",
  "plane_workspace": "your-workspace-slug",
  "plane_project_id": "uuid-from-plane"
}

3. Create your first issue

# In Claude Code — the /issue skill reads the config and dispatches to Plane
> /issue "Add user authentication" --type feature --priority 2

4. Check the board

Issues appear immediately in the Plane project board. Use mcp__plane__list_project_issues to query them from within a Claude Code session without leaving the terminal.

Prompt: wire up issue tracking for a new project
I want to add Plane issue tracking to my project. My Plane workspace is [slug] and the project ID is [uuid]. The issue prefix should be [PROJ].

1. Create .specflow/config.json with issue_backend: "plane" and the workspace/project coordinates.
2. Verify the config by calling mcp__plane__list_project_issues and confirming it returns without error.
3. Create a test issue titled "Project tracking configured" as a chore, then close it.

After that, use the /issue skill for all future issue creation in this project.
